Hostkind

A self-hosted control plane for game servers and long-running processes. AGPL-3.0, public source, installers for Windows and Linux.

Why it exists

Every game ships its own server and its own way of running it. Minecraft wants a Java version and an EULA flag, Valheim and Palworld want SteamCMD, Terraria wants a config file edited by hand. The usual answer is a paid hosting panel, which also means someone else holds the world files.

Hostkind is the opposite arrangement: one local application that supervises the processes, streams their consoles, watches memory and player counts, handles backups and updates, and asks for no account. It keeps the files where they already are instead of on someone else's server.

What was actually hard

The first hard decision was to stay in a single Node.js process. No Docker, no external database, no Redis. That constraint decides a lot of smaller ones: state lives in SQLite, long-running work is recorded as jobs that can be inspected after a crash, and the panel has to survive an operation being interrupted halfway through. Earlier versions leaned on containers and separate services, and installs, upgrades and crash recovery were all worse for it.

The second was the module boundary. Minecraft, Terraria, Valheim and Palworld each install, become ready and shut down in their own way, and writing that into the core would have made every new game a rewrite. Process management stayed generic; launch preparation, readiness detection, graceful shutdown, console parsing and content workflows live in per-game modules under lib/modules/. Adding another game then meant adding a module, not touching the supervisor.

The third was packaging. Three platforms, two installer formats on Linux, an Electron wrapper for the desktop build, and an unsigned Windows installer that Windows will warn about. That warning is a real product problem: the honest fix is code signing, and until then the docs have to tell people to use the portable zip rather than switch off Defender.

Backups were the part I underestimated. A backup that cannot be verified is a hope, so the panel verifies archives, keeps retention rules, and makes destructive actions take a second confirmation with their own token.

What I'd change

I would draw the module boundary before the first game module, instead of after the second one forced it. The generic core is the reason the app still grows, and it arrived later than it should have.

I would sign the Windows installer before the first public release. It is boring work with no demo value, which is exactly why it kept slipping, and it costs every user a scary dialog until it is done.

I would also ship the "needs attention" overview earlier. Crashes, stale backups and pending updates were all visible somewhere in the app for a while, but not in one place, and that one list is what makes the panel feel like a control plane rather than a folder of buttons.
