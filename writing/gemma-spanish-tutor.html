Training a 2B Spanish tutor on a laptop GPU, and the rounds that did not work

November 2026

I trained gemma4:e2b, a 2B model, to act as a Spanish tutor for Korean speakers. It runs locally in Ollama on a 12 GB laptop GPU. This is a learning project and a prototype, so the rounds that failed are in here next to the one that worked.

What the model has to do

The learner writes a Spanish sentence and asks, in Korean, whether it is right. The tutor rewrites it, names what changed, explains the rule in Korean and gives one practice exercise. That is four jobs in one answer, and only the first one is easy to check automatically.

Learner: "Si el autobús llegaría a tiempo, no perderíamos el tour. ¿Está bien?"

Tutor: it should be "Si el autobús llegara a tiempo, no perderíamos el tour", because llegaría became llegara. Then the rule in Korean, and one exercise.

The rewrite is right. The explanation in the actual v4 output was not: it mixed up the imperfect subjunctive and the conditional. That happened often enough to matter, and it is the reason a later part of this project exists.

The test set came first, eventually

The first versions were scored on a 70-item set and a 100-item dev set. Those numbers are still in the repo. The set that counts was frozen before round 4 and kept out of every training run: 208 items, half with a real error and half already correct, written by a larger model and checked by blind judges. The correct half turned out to be the important one.

Why: the stock model rewrote two out of three correct sentences. It was helpful in the way a bad editor is helpful. Any fine-tune that learns to leave good sentences alone will look much better on a set like this, and that is mostly what happened.

Data that is correct by construction

Training data came from two places. Conjugations and corrections were generated so they are correct by construction: a verb table and a correction rule either produce a right answer or they do not run. Explanations cannot be generated that way, so those were distilled from gemma4:26b and reviewed by hand.

Then QLoRA SFT on 12 GB of VRAM, merge, convert to GGUF, quantise to Q4_K_M, import into Ollama. The first eval after that was clarifying: the model had learned the format perfectly and was using it to praise wrong sentences.

The rounds

Round 1 was that SFT model. Then two GRPO rounds with automatic verifiers as rewards, hard-prompt filtering and significance tests. Rounds 3 and 4 compared a check-first prompt with a rewrite-first one, added teacher-written items for the cases the model kept failing, and self-distilled the training set from the better rounds. The frozen set stayed frozen.

On the 208 items from round 4:

test_set_v4.jsonl, 104 items with errors and 104 correct
model total errors caught correct left alone
stock gemma4:e2b 123 90 33
grpo3 167 71 96
v4 (SFT) 177 81 96
grpo4 (v4 + GRPO) 179 82 97

The jump from 123 to 177 is real, and it is mostly the third column: the fine-tune stopped breaking sentences that were fine. On the second column it was behind the stock model, 81 against 90, p=0.064. So the headline number flatters the model in exactly the way the headline number usually does.

GRPO is the clearest failure. On top of v4 it moved the total from 177 to 179, p=0.75, for a night of training per round. The reward checked the verdict and the rewritten Spanish, because those are checkable. The explanation, which is the part learners read, was not in the reward at all.

A judge changed the answer

A 2B model can produce the right correction and a wrong explanation, and string matching cannot see the difference. So I extracted a separate judge: a blind gemma4:26b scoring the answers with no knowledge of which model produced them, run through a small CLI I now keep as ollama-rubric.

It found real errors. On one item the model correctly confirmed that "A mis amigos les gustaban los perros de la calle" was grammatical, then translated perros as street cats. On another it called pierdas an infinitive.

The last round, v5, added self-distillation with the 26B model as a fallback on hard errors. On a newer frozen set the mechanical score was 184/208; with the blind judge it was 181, 95% interval 81.8% to 90.9%. The stock model landed at 158 and v4 at 166 under the same judge.

test_set_v4.1.jsonl, all 208 items, Ollama 0.40.7
model mechanical judged errors median latency
stock gemma4:e2b 170 158 84 0.72 s
v4 174 166 75 0.50 s
v5 184 181 90 0.99 s

What I would do differently

Build the frozen set and the judge before the first training run. Two of the rounds were spent optimizing a number that the evaluation setup could not measure properly, and when the judge arrived it reordered the models.

Skip GRPO for this task. If the reward cannot see the explanation, the policy will not improve the explanation. A better use of that GPU time would have been more teacher-written explanation data, reviewed by someone who speaks Korean.

Limits

  • The test items were generated by gemma4:26b, not written by native speakers. They are checked, not authoritative.
  • I do not speak Korean. The explanations were checked by a model judge, and a 30-item calibration set is still waiting for a Korean speaker to label it.
  • Text only. llama.cpp's converter drops Gemma 4's vision and audio encoders, so the app has no listening or speaking practice.
  • The weights are not published. You can train them locally with the scripts in the repo.
